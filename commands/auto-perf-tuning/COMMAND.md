# Auto Performance Tuning Command

このコマンドは、パフォーマンス改善作業を自動的に実行します。調査、実装、ベンチマーク検証、PR作成まで一貫して行います。

## 基本方針

- **測定可能な改善**: ベンチマークで改善を定量的に測定
- **機能維持**: 既存の振る舞いを変更せず、パフォーマンスのみ改善
- **段階的改善**: 1つの改善に集中し、複数の変更を混在させない
- **自動化**: 調査からPR作成まで自動実行

## 使用方法

```
/auto-perf-tuning
```

## デフォルト設定

- **作業ブランチ**: `perf/auto-perf-tuning-YYYY-MM-DD` （現在日付）
- **PRタイトル**: `perf(core): Automated performance tuning by Claude`
- **改善指標**: 実行全体の2%以上の改善
- **調査サブエージェント数**: 2
- **サブエージェントのモデル**: `sonnet`

## 進捗チェックリスト

作業は以下の順序で進行します：

```
- [ ] 1. ブランチ準備
- [ ] 2. 既存PRの確認
- [ ] 3. 調査・計画
- [ ] 4. 実装
- [ ] 5. ベンチマーク・検証
- [ ] 6. コミット
- [ ] 7. ローカルでのレビュー
- [ ] 8. PR作成・更新
```

## 作業手順

### 1. ブランチ準備

- 最新状態取得: `git pull origin main`
  - リポジトリごとにdevelopブランチなど異なる可能性があるので適切なブランチから子ブランチを作成する用意を行う。
- 作業ブランチ作成: `perf/auto-perf-tuning-YYYY-MM-DD`
  - 既存の同名ブランチがある場合は、ブランチ名にナンバリングを追加（例: `perf/auto-perf-tuning-YYYY-MM-DD-No`）

### 2. 既存PRの確認

- 作業ブランチに対するPRがすでに存在するか確認する
  - `gh pr list --head [ブランチ名]` で確認
- PRが存在する場合:
  - PRの説明とレビューコメントを読み、コンテキストを把握する
  - 前回の改善内容を理解し、重複を避ける

### 3. 調査・計画

#### 3.1 リポジトリ構造の把握

まずリポジトリの構造・処理フローを把握する：

- プロジェクトのREADME、CLAUDE.md、ドキュメントを読む
- エントリーポイントを特定（CLI、API、主要な処理フロー）
- 計測対象となる主要な処理の実装箇所を特定

#### 3.2 並列調査の実施

**調査サブエージェント数** 分の重複しない調査スコープを設計し、各スコープを担当するサブエージェント（モデル: **サブエージェントのモデル**）を並列に起動する。

**スコープ設計の原則**:

- リポジトリの特性に応じて自由に決定してよい
- 各スコープが重複しないようにする
- 計測可能な改善ポイントを探す

**スコープ例**:

1. **クリティカルパス特定**
   - ボトルネック箇所の特定
   - プロファイリングツールの使用（Node.js Profiler、Chrome DevToolsなど）
   - 実行時間の測定

2. **I/O・外部通信**
   - 不要な再読み込み
   - 同期I/O（fs.readFileSync等）
   - バッファサイズの最適化
   - ネットワークリクエストの並列化

3. **データ構造・アルゴリズム**
   - 計算量の改善（O(n²) → O(n log n) など）
   - 文字列操作の最適化
   - コレクション選択（Array vs Set vs Map）
   - ループの最適化

4. **並列化・非同期**
   - 直列処理の並列化余地
   - 不要な逐次await
   - Promise.allの活用
   - Worker Threadsの活用

5. **依存ライブラリ・初期化コスト**
   - 軽量代替ライブラリ（例: moment → dayjs）
   - 遅延ロード（lazy import）
   - 不要な依存関係の削除
   - 初期化処理の最適化

#### 3.3 改善計画の立案

全エージェントの報告を統合し、改善計画を立てる：

- **複数の改善点が見つかった場合でも、必ず1つだけに絞る**
- 今回のチューニングで最もインパクトの大きい変更1つのみに集中する
- **改善指標** を満たす改善が見つからなかった場合、調査結果を報告して作業を終了する

### 4. 実装

計画を実装する：

- 最小単位で実装し、段階的に確認する
- 既存テストが壊れないことを確認しながら進める
- 機能的な変更は行わず、既存の振る舞いを維持する

### 5. ベンチマーク・検証

#### 5.1 ベンチマーク実行

- ベンチマークを実行し、変更が **改善指標** を満たすことを測定で確認する
- 改善前と改善後の実行時間を複数回測定し、平均値と標準偏差を記録する
- 測定環境の情報も記録する（CPU、メモリ、Node.jsバージョン等）

#### 5.2 本番環境シミュレーション

テスト環境が本番環境と特性が大きく異なる場合（例: インメモリDB vs クラウドDB、モックAPIレスポンス等）、本番相当のレイテンシを注入したシミュレーションで改善率を検証する：

- シミュレーション値の根拠を明記する（本番レイテンシの実測値または公式ドキュメント参照）
- コミットメッセージに記載する

#### 5.3 ベンチマークテストの実装

ベンチマークテストを実装する際の注意点：

- デフォルトタイムアウト（通常5000ms）を考慮する
- 実行時間を見積もってから実装する
- タイムアウトを超過する場合は個別設定する:
  ```typescript
  it("performance test", async () => {
    // テスト内容
  }, 10000); // 10秒タイムアウト
  ```

#### 5.4 リグレッション確認

lint と test を実行し、リグレッションがないことを確認する：

```bash
npm run lint
npm test
npm run build
```

#### 5.5 改善指標の判定

- **改善指標** を満たさなかった場合、変更をrevertし、調査結果を報告して作業を終了する
- 満たした場合、次のステップへ進む

### 6. コミット

`perf` プレフィックスでコミットする：

```bash
git add .
git commit -m "perf(scope): 改善内容の概要

対応内容:
- 具体的な変更内容1
- 具体的な変更内容2

ベンチマーク結果:
- 改善前: XXms (平均値 ± 標準偏差)
- 改善後: YYms (平均値 ± 標準偏差)
- 改善率: ZZ%

測定環境:
- CPU: ...
- メモリ: ...
- Node.js: vX.Y.Z

Co-Authored-By: Claude Sonnet 4.5 <noreply@anthropic.com>"
```

コミットボディに対応内容とベンチマーク結果を詳しく記載する。

### 7. ローカルでのレビュー

ローカルで複数のサブエージェントにレビューさせる：

1. **レビューサブエージェントの起動**
   - 2-3のサブエージェント（モデル: **サブエージェントのモデル**）を並列に起動
   - 各サブエージェントは異なる視点でレビューする:
     - パフォーマンス改善の妥当性
     - コード品質（可読性、保守性）
     - テストカバレッジ

2. **修正サイクル**
   - 対応が必要な指摘があった場合、修正して再度レビューする
   - 修正時は `git commit --amend` を使い、コミットは1つにする
   - 修正箇所がなくなるまで繰り返す

3. **Push**
   - 修正箇所がなくなった場合、pushする:
     ```bash
     git push -u origin perf/auto-perf-tuning-YYYY-MM-DD
     ```

### 8. PR作成・更新

#### 8.1 既存PR確認

PRがすでに存在するか確認する:

```bash
gh pr list --head perf/auto-perf-tuning-YYYY-MM-DD
```

#### 8.2 PR作成（新規の場合）

```bash
gh pr create --title "PRタイトル" --body "$(cat <<'EOF'
## Summary
[改善内容の概要を簡潔に記述]

## Changes
[具体的な変更内容]

## Benchmark Results
### Before
- 実行時間: XXms (平均値 ± 標準偏差)

### After
- 実行時間: YYms (平均値 ± 標準偏差)

### Improvement
- 改善率: ZZ%

### Measurement Environment
- CPU: ...
- Memory: ...
- Node.js: vX.Y.Z

## Test plan
- [x] ベンチマークテスト実行
- [x] 既存テストの通過確認
- [x] Lint・型チェックの通過確認

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

#### 8.3 PR更新（既存の場合）

既存PRにコメントを追加して更新内容を説明する:

```bash
gh pr comment [PR番号] --body "追加の改善内容を反映しました。

## Summary
[改善内容の概要]

## Benchmark Results
[ベンチマーク結果]
"
```

## 注意事項

- **必ずフィーチャーブランチで作業**: mainブランチへの直接コミット禁止
- **最新状態の取得**: 作業開始前に必ず `git pull origin main`
- **1つの改善に集中**: 複数の改善を混在させない
- **機能維持**: 既存の振る舞いを変更しない
- **測定可能な改善**: ベンチマークで改善を定量的に測定する
- **改善指標の遵守**: 改善指標を満たさない場合は作業を終了する
